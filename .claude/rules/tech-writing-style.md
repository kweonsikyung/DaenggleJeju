## Tech Writing Style

**Impact: MEDIUM (일관된 문체·구조로 독자 신뢰도와 가독성 향상)**

**적용 범위**: GitHub Wiki, 기술 블로그 글. README·코드 주석에는 적용하지 않음 — README는 `~함` / `~한다` 의 간결체를 유지함.

기술 글은 문체와 구조가 일관돼야 읽는 사람이 내용에 집중할 수 있어요. 합니다체보다 해요체가 부드럽고 친근하며, 트러블슈팅은 반드시 문제 → 원인 → 해결 순서로 서술해야 독자가 자신의 상황과 대조하기 쉬워요.

## 문체 규칙

**Incorrect (합니다체 — 딱딱하고 보고서 느낌):**

```markdown
이 오류는 tsup이 jsx를 변환할 때 발생합니다.
원인은 esbuild의 기본 JSX 변환 방식이 classic이기 때문입니다.
해결하려면 esbuildOptions에서 jsx를 automatic으로 설정해야 합니다.
```

**Correct (해요체 — 친근하고 기술 블로그 느낌):**

```markdown
이 오류는 tsup이 jsx를 변환할 때 생겨요.
esbuild 기본 JSX 변환이 classic이라서 `import React`가 없는 파일에서는 바로 터지는 거예요.
그래서 `esbuildOptions`에서 `jsx: "automatic"`으로 바꿔줬더니 해결됐어요.
```

## 시제 규칙

글의 목적에 따라 시제를 구분해요.

- **회고·작업 기록** — 이미 일어난 일이므로 과거형으로 써요
- **튜토리얼·개념 설명** — 독자가 따라하는 내용이므로 현재형으로 써요

**Incorrect (회고인데 현재형 — 지금 일어나는 일처럼 읽혀서 어색함):**

```markdown
빌드가 실패해요. 원인을 찾아봐요. esbuild 옵션 문제예요. jsx 설정을 바꿔요.
```

**Correct (회고는 과거형 — 흐름이 자연스럽게 읽힘):**

```markdown
빌드가 계속 실패해서 로그를 뜯어봤어요.
esbuild 옵션이 잘못 설정돼 있었고, jsx를 automatic으로 바꾸니까 해결됐어요.
```

**Correct (튜토리얼은 현재형 — 독자가 따라하는 맥락):**

```markdown
`esbuildOptions`에서 `jsx: "automatic"`으로 설정하면 해결돼요.
```

## 연결어 규칙

문장을 툭툭 끊지 않고 연결어로 흐름을 이어줘요.

| 상황      | 쓰는 연결어                     |
| --------- | ------------------------------- |
| 원인 설명 | `~라서`, `~때문에`, `~이었는데` |
| 흐름 전환 | `그런데`, `근데`, `그러다가`    |
| 결과·결론 | `그래서`, `결국`, `~하니까`     |
| 추가 설명 | `그리고`, `또`, `~기도 했어요`  |

**Incorrect (연결어 없이 툭툭 끊김 — 인과관계가 안 보임):**

```markdown
빌드가 실패했어요. esbuild 옵션 문제였어요. jsx 설정을 바꿨어요. 해결됐어요.
```

**Correct (연결어로 흐름을 이어줌 — 읽으면서 상황이 그려짐):**

```markdown
빌드가 계속 실패해서 로그를 뜯어봤어요. esbuild가 classic JSX를 기대하고 있었는데,
소스엔 `import React`가 없었던 거예요. `jsx: "automatic"`으로 바꾸니까 바로 됐어요.
```

## 글쓴이 환경 규칙

글 앞부분에 항상 환경 블록을 넣어요. 독자가 자기 환경과 비교해서 삽질을 줄일 수 있어요.

환경 블록에는 글의 주제와 직접 관련된 패키지만 명시해요 — 관련 없는 패키지까지 전부 나열하면 오히려 노이즈가 돼요.

**Correct:**

```markdown
### 글쓴이 환경

| 항목    | 버전              |
| ------- | ----------------- |
| Node.js | v20.11            |
| React   | 18.3              |
| tsup    | 8.0               |
| esbuild | 0.20.1            |
| OS      | macOS Sonoma 14.3 |
```

버전 표기는 `패키지명 숫자` 형식으로 통일해요. `v18`, `React 18.x`, `~18.0` 처럼 글마다 다르게 쓰지 않아요.

환경 블록에 없는 패키지가 본문에서 처음 등장하면, 그 자리에서 버전을 인라인으로 명시해요:

```markdown
`esbuild@0.20.1`에서 확인한 동작이라 다른 버전에서는 다를 수 있어요.
```

**어떤 패키지를 넣을지 기준:**

| 넣어요                                | 안 넣어요               |
| ------------------------------------- | ----------------------- |
| 글에서 직접 언급하는 패키지           | 간접 의존성 패키지      |
| 버전에 따라 동작이 달라지는 도구      | 글 주제와 무관한 패키지 |
| 런타임·OS처럼 환경 자체를 결정하는 것 | 사소한 유틸리티         |

## 트러블슈팅 구조 규칙

하나의 문제는 하나의 섹션. 여러 문제를 한 섹션에 묶지 않아요.

**Incorrect (여러 문제를 한 번에 나열):**

```markdown
## 발생한 문제들

- 빌드 실패, 타입 오류, 런타임 에러가 발생했다.
- 원인은 각각 A, B, C다.
- 해결책은 X, Y, Z다.
```

**Correct (문제 하나 → 원인 → 해결, 반복):**

```markdown
## 문제 1. 빌드 실패

**왜 생겼나요?** esbuild가 classic JSX를 기대하는데 소스에 `import React`가 없어요.
**어떻게 해결했나요?** `jsx: "automatic"` 옵션을 추가했어요.

## 문제 2. 타입 오류

...
```

## 코드·표 규칙

- 인라인 코드는 `` ` `` 으로 감싸요: `tsup.config.ts`, `"use client"`
- 코드 블록은 언어 명시: ` ```ts `, ` ```json `, ` ```bash `
- 표는 3열 이하로 유지해요 — 열이 많으면 읽기 어려워요

## 마무리 멘트 규칙

글을 뚝 끊지 않고 독자와 연결되는 문장으로 마무리해요. 글쓴이의 경험이 독자에게 열려 있다는 느낌을 주는 게 포인트예요.

**Incorrect (뚝 끊기는 마무리 — 글이 그냥 끝나버리는 느낌):**

```markdown
이렇게 설정하면 문제가 해결됩니다. 이상입니다.
```

**Correct (독자에게 열린 마무리 — 경험을 나누고 싶어하는 느낌):**

```markdown
비슷한 상황을 겪고 계시다면 편하게 댓글이나 이슈로 남겨 주세요.
저도 아직 모르는 게 많아서, 다른 분들이 같은 상황에서 어떻게 풀었는지 궁금하기도 해요.
읽어 주셔서 감사합니다.
```

마무리 문장은 이 세 흐름을 자연스럽게 이어줘요.

1. **경험 나눔 유도** — "비슷한 상황이면 언제든 얘기해요" 류의 열린 초대
2. **공감·궁금증** — 글쓴이도 여전히 배우고 있다는 걸 드러내서 거리를 좁혀줘요
3. **감사 인사** — "읽어 주셔서 감사합니다"로 마무리
